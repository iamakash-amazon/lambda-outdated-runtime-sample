Why upgrade

  • 1.31 extended support ends 2026-11-26 (13 days) — health-td-eks-foreach-a and payments-prod. After that date EKS auto-upgrades the cluster.
  • 1.32 is in extended support since 2026-03-23 (ends 2027-03-23) — health-td-eks-literal, health-td-eks-conditional. Per-cluster-hour surcharge.
  • 1.33 is in extended support since 2026-07-29 (ends 2027-07-29) — health-td-eks-variable, health-td-eks-tfvars-json, health-td-eks-cfn.
  • 1.23 / 1.24 / 1.28 / 1.30 are past end of extended support — EKS has auto-upgraded any live cluster; the code no longer matches reality (stale-code and eksctl cases).
  • Amazon Linux 2 retirement — AL2 EKS AMIs end at 1.32; payments-prod and legacy-reporting node groups are AL2 and must move to AL2023 at their 1.32 → 1.33 hop.

Our recommendation

Recommended end target is 1.37 (standard support until 2027-12-01); 1.36 (until 2027-08-02) is also supported for more than 180 days. EKS upgrades in place one minor at a time.

A — Full sequence to 1.37, one hop per run, validating between each. The longest path is 1.31 → 1.32 → … → 1.37 (six hops).
B — Stop at 1.36 (supported for more than 180 days). One hop fewer per cluster.
C — Blue/Green for the past-end-of-support eksctl cluster legacy-reporting (new 1.37 cluster with AL2023 nodes, then cut over). This avoids replaying 1.24-era manifests through every hop.

✅ Recommended: A, one hop now. Do the hop each cluster needs most urgently (this run), then repeat. 1.31 extended support ends in 13 days, and 1.32/1.33 cost an extended-support surcharge.

Roadmap to Production

Everything you need to take the transformed code safely to production is on this tab. EKS operates under a shared-responsibility model: AWS upgrades the control plane; you own the add-ons, the data plane, and validating that your workloads still run.

⚠️ This repository auto-deploys: .github/workflows/deploy.yml runs terraform apply -auto-approve on every push to main. Merging the root Terraform changes upgrades health-td-eks-* control planes right away. Run terraform plan on the review branch first.

The upgrade order (and why)

  1. Assess readiness: Cluster Insights plus a deprecated-API scan. An API that is still in use and removed in the target version is rejected as soon as the control plane advances.
  2. Fix the IaC (this transformation). Reviewable and repeatable across environments.
  3. Fix the workloads (app team). API removals and OS/cgroup changes break apps, not infrastructure, so fix them before the API server changes.
  4. Upgrade the control plane. AWS-managed, can be rolled back within 7 days, must go before the data plane.
  5. Upgrade the add-ons (VPC CNI, CoreDNS, kube-proxy, CSI). EKS does NOT upgrade them for you; one minor at a time.
  6. Upgrade the data plane (nodes) to match. AL2→AL2023 happens here.
  7. Validate, then promote to the next environment.
ℹ️ Version-skew safety net: on Kubernetes ≥ 1.28, kubelet can trail the API server by up to 3 minor versions (n-3). That is why "control plane first, nodes after" is safe.

Phases

  1. Phase 0 · Plan & assess: confirm the hop; run aws eks describe-cluster; check node/kubelet versions; run Cluster Insights; read release notes; take a backup.
  2. Phase 1 · Set up a safe rollout path: Dev → UAT/Staging → Production; never upgrade prod first.
  3. Phase 2 · Upgrade the IaC: apply the reviewed diff and confirm the plan is in-place, not destroy/recreate.
  4. Phase 3 · Remediate workloads: scan for removed APIs (kubent, pluto); PDBs + topology spread; cgroup v2 runtime fixes.
  5. Phase 4 · Execute per environment: control plane → add-ons → data plane; clear the validation gate before promoting.
  6. Phase 5 · Post-upgrade: confirm versions, watch for OOMKills, redeploy Fargate workloads, update runbooks.

Availability during the node roll (PDBs + spread)

Draining uses the Eviction API, which respects PodDisruptionBudgets. An overly strict PDB (maxUnavailable: 0) blocks the roll with PodEvictionFailure.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: { name: myapp }
spec:
  minAvailable: "80%"
  selector: { matchLabels: { app: myapp } }
---
# in the Deployment pod spec:
      topologySpreadConstraints:
        - maxSkew: 2
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector: { matchLabels: { app: myapp } }

Common workload checklist

  • Deprecated/removed APIs migrated (Ingress, CronJob, PDB, HPA, RBAC, flowcontrol).
  • In-tree storage → CSI. No Docker-socket dependency.
  • Resource requests/limits set; PDB + topology spread on user-facing workloads.
  • Accurate probes; graceful SIGTERM; image tags pinned and re-pullable.

Validation gate (run in EVERY environment before promoting)

✅ Control plane AND nodes report the target version.
✅ All nodes Ready; no OOMKilled / CrashLoopBackOff pods.
✅ Add-ons healthy (CoreDNS resolving, CNI assigning IPs, CSI mounting).
✅ No PodEvictionFailure during the node roll.
✅ Application smoke tests pass.

KMS / encryption prerequisite

No customer-managed KMS key is configured in this repo. If you add one, make sure its key policy allows CloudWatch Logs and the Auto Scaling service-linked role (kms:CreateGrant). Missing grants fail at apply time.

Dev → UAT / Staging → Production

One minor at a time · Blue/Green alternative

Repeat Phases 2–5 for each hop and never skip a minor version. To get there in one operational move (recommended for legacy-reporting), use Blue/Green: create a new cluster at the target version, deploy the workloads, shift traffic, then retire the old cluster. You can roll back an in-place control-plane upgrade within 7 days.
